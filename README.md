# RECsysX
Recommendation & Graph Intelligence

RECsysX was built to compare conventional collaborative filtering with graph-based
recommendation on MovieLens-1M. It checks where the graph models help, if anywhere: overall
ranking quality, cold-start users and items, and training data that gets sparser.

Next to the individual models there is a two-stage pipeline:

- FAISS candidate retrieval
- a learned ranker
- diversity re-ranking
- PostgreSQL as the store the pipeline reads user histories from and writes recommendations to

The full write-up with all experiments is in [REPORT.md](REPORT.md). This README is the short
version plus everything needed to run the code.

## Overview

- 11 recommenders trained and evaluated with one shared protocol: popularity (3 variants),
  ItemKNN, MF-BPR, two-tower, Node2Vec, GraphSAGE, GAT, LightGCN and a hybrid content + graph GNN
- time-based split without leakage, results reported per user group (warm / sparse / cold), 3 seeds
  and paired significance tests
- cold-start experiments: users without history, simulated new items, and new users who reveal
  k = 0..10 ratings
- a sparsity experiment with 100 / 50 / 20 / 10% of the training data
- FAISS retrieval (exact, IVF, HNSW), rankers (logistic regression, XGBoost LambdaMART, listwise
  MLP), MMR diversity re-ranking, exposure analysis, error analysis
- every number in this README and in the report is generated by a script into `results/`

## Problem

Top-K recommendation from implicit feedback: a rating of 4-5 stars counts as a positive. Using
only what happened before a cutoff date, the system recommends 20 movies per user that the user
has not rated yet. A list is good if it contains the movies the user liked after the cutoff. On the
user-movie graph this is link prediction: rank the edges that will appear above the ones that
will not.

## Main Question

**Does graph-based representation learning improve recommendation and cold-start performance
compared with conventional collaborative filtering?**

Short answer from the experiments:

- Graph propagation: yes, a little. LightGCN beats MF-BPR by +0.0066 recall@20 (95% CI
  [+0.0030, +0.0103]). The gain is largest for sparse users.
- Learned message passing: no. GraphSAGE and GAT end up at MF level.
- Sparse data: the graph models lose less. With 10% of the training data MF keeps 78% of its
  recall, LightGCN 83%, GAT 86% and the hybrid 88%.
- Cold-start: nothing beats demographic popularity for users with no history. For new items
  only content helps.

## Dataset

[MovieLens-1M](https://grouplens.org/datasets/movielens/1m/): 1,000,209 ratings from 6,040 users
on 3,706 movies (2000-2003), with user demographics and movie genres, year and title. It was
chosen over the alternatives for these reasons:

- ML-100K is too small for the sparsity and per-group results.
- ML-25M does not fit repeated full-graph GAT training on a 6 GB GPU.
- Amazon/Yelp-style datasets have no usable item metadata in the common versions, or become
  extremely sparse after the usual k-core filtering.

The license does not allow redistribution, so the data is downloaded by a script. Details are in
[data/README.md](data/README.md).

## EDA

Notebook: [01_eda.ipynb](notebooks/01_eda.ipynb). Two findings shaped the project.

- Long tail. The top 20% of movies receive 65% of the ratings, and 446 movies have fewer than
  10.
- Burst behaviour. 63% of the users gave all their ratings within 24 hours of their first one.
  A plain train/val/test split on time would validate on brand-new users and test on long-term
  users. The split is therefore one global time cutoff (the 80% quantile, 2 Dec 2000), with the
  users active after it divided into disjoint validation and test users. There are 881 of each;
  the test users are 487 warm, 73 sparse and 321 cold.

![ratings over time and burst behaviour](results/figures/eda_ratings_time.png)

## Feature Engineering

- Content vectors are the inputs of the two-tower and hybrid models:
  - movies: 18 genres + year + decade + a 16-d SVD of the title tf-idf
  - users: one-hot gender, age, occupation and zip region
- 32 ranking features per (user, candidate): user activity, pickiness, recency, genre entropy
  and mainstreamness; item popularity (all-time and last 30 days), smoothed rating and year; the
  scores of every trained model; genre affinity; popularity and year gaps.
- No leakage: all statistics use only pre-cutoff ratings. A unit test changes every post-cutoff
  rating and checks that no feature moves.

## Models

| model | idea | file |
|---|---|---|
| Popularity (all-time / last 7 days / per gender x age) | non-personalised baselines | `models/popularity.py` |
| ItemKNN | item-item cosine on co-likes, no training | `models/itemknn.py` |
| MF-BPR | user/item embeddings, BPR loss, sampled negatives | `models/mf.py` |
| Two-Tower | id + feature towers, in-batch softmax with logQ correction | `models/two_tower.py` |
| Node2Vec | biased random walks + skip-gram on the user-item graph | `models/node2vec.py` |
| GraphSAGE | mean-aggregation GNN, BPR link prediction | `models/gnn.py` |
| GAT | attention GNN, same training | `models/gnn.py` |
| LightGCN | weight-free normalised propagation, same training (added after the GNN diagnostics) | `models/gnn.py` |
| Hybrid | LightGCN propagation with id embedding + content projection | `models/gnn.py` |

All embedding models use 64 dimensions. Each has an "unknown user" embedding trained through id
dropout, so users without history get a learned representation instead of a random one.

## Recommendation Pipeline

```
user id ──> PostgreSQL (or memory): rated movies
               │
               ▼
        hybrid GNN user vector ──> FAISS IndexFlatIP over item vectors
               │                     top-200 unseen movies (over-fetch + filter)
               ▼
        32 ranking features per candidate (statistics + scores of all models)
               │
               ▼
        XGBoost LambdaMART ranker, trained only on data before the cutoff
               │
               ▼
        MMR re-ranking, genre similarity, lambda = 0.9 ──> top-10
```

The retriever, ranker, N and lambda were chosen on validation users and are read from the
experiment outputs (`checkpoints/ranking/ranking_meta.json` written by `run_ranking.py`,
`results/tables/diversity_selected.json`), not hard-coded. One request
takes 18.7 ms on a laptop CPU (19.2 ms with the history read from PostgreSQL).

Notes on retrieval:

- The candidate generator limits everything downstream. About 48% of a user's future positives
  are among the 200 candidates. For movies outside the 20% most popular, the retriever is the

  (HNSW 0.8 ms).

That gain is partly optimistic. The validation users' labels come from the same period as the
test users', and the ranker had learned period-specific trends: release year and recent popularity
were its most important features after the retrieval rank. To measure this, a strictly temporal
ranker was trained only on data before the cutoff, with all score models retrained on an earlier
cutoff. It reaches 0.1329, so about half of the gain is real and half was information about
the test period. The final pipeline uses the strictly temporal ranker.

## Graph ML

Getting the GNNs to work took most of the debugging time. The full log is in
[gnn_training_diagnostics.txt](results/logs/gnn_training_diagnostics.txt).

- Early stopping was too impatient. GraphSAGE first looked like popularity: its validation
  curve is flat for many epochs before it improves. Patience was raised from 10 to 20 for MF, the
  two-tower model and the GNNs.
- Cold users broke GAT. Logging the validation metric per user group showed that warm users
  got better while cold users fell from 0.11 to 0.004 recall@20. The "unknown user" embedding was
  trained with the users' edges still in the graph, while a real cold user has none. The fix
  removes the dropped users' edges during training (`cold_simulation`). It is kept as an ablation.
- Over-smoothing. The graph is extremely dense at two hops: a typical user shares a liked movie
  with 4,915 of 5,395 other users. Propagating genre profiles with mean aggregation makes users
  almost identical after three steps (mean cosine 0.986). Every GNN picked 1 layer in tuning, and
  with longer patience 2 layers were about equal.
- Learned transforms vs. propagation. LightGCN (no weights, no nonlinearity) was added to
  separate the two. It beats MF, while GraphSAGE and GAT do not.
- Node2Vec. It is significantly worse than MF, and its link-prediction AUC on sparse users is
  0.30, worse than random.

## Diversity

MMR re-ranking on the final ranker's top 200 candidates, operating point picked on validation
users:

- Genre similarity, lambda = 0.9 (selected): genre diversity@10 0.670 -> 0.701 for -0.4%
  NDCG@10.
- Stronger lambda gets expensive: lambda = 0.5 reaches 0.870 diversity but costs 12% NDCG.
- MF-embedding similarity hardly changes genre diversity but raises coverage (0.098 -> 0.168)
  and novelty at lambda = 0.5, for -6.6% NDCG.

Exposure is very concentrated for every model. Test users actually liked 2,980 different movies
(Gini 0.70). The models show 97-779 movies in their top-10 lists (Gini 0.94-0.99), and the
learned ranker narrows the lists further.

- GNN design. Without cold simulation GAT loses 0.04 recall@20 on cold users, and without the
  unknown-user embedding cold users get random lists. Target-edge removal makes no measurable
  difference with 1 layer.
- Ranking. Removing the graph-model scores from the ranker costs 0.004 recall@20, and the ranker
  with only the retrieval score/rank gains nothing.

All ablations: [ablation_results.csv](results/tables/ablation_results.csv). The tables are in
section 25 of the report.

## Error Analysis

- Retrieval is the bottleneck outside the head. 84% of all test positives are not in the
  top 20 of any model. For the final pipeline, 45% of the popular (head) targets are never
  retrieved and 43% are retrieved but ranked below 20. For less popular targets, 94-100% are never
  retrieved.
- The heaviest users (>200 training positives) are among the hardest: their later likes are
  much less popular than their history.
- Narrow-taste users are where personalization pays off. Popularity drops to 0.078 there, while
  the pipeline reaches 0.146.
- One hypothesis that did not hold. GraphSAGE losing to MF on users whose movies are all
  blockbusters is not supported (Spearman -0.01, p = 0.76).

Concrete cases are picked by fixed rules in
[error_examples.md](results/tables/error_examples.md) and
[recommendation_examples.md](results/tables/recommendation_examples.md).

## Limitations

- One dataset with an unusual sign-up burst pattern. MovieLens shows popular movies during
  sign-up, which favours popularity.
- Thin content features: genres, year and title.
- Small sparse group (73 test users).
- Limited tuning: a small coordinate-wise tuning budget, and some experiments use a single
  seed.
- Offline evaluation only. It cannot say whether unrated recommendations would have been
  liked.
- Small catalog. With 3.7k movies, the FAISS experiments test correctness and exact-search
  latency, not large-scale approximate search.

PostgreSQL. Set `DATABASE_URL` (e.g. `postgresql://user:pass@localhost:5432/recsysx`) to use an
existing server. Without it, the database scripts start a local server in `.pgdata/` through the
optional `pgserver` package (`pip install pgserver`). That is what I used on a laptop without a
PostgreSQL install. The database holds users, movies and ratings. The final pipeline reads user
histories from it at request time and writes recommendations back. Training reads the Parquet
snapshot instead, because it is faster and needs no server. `scripts/db_check.py` verifies with 13
SQL checks that the two agree, including a full round trip of the ratings table.

Weights & Biases. Optional. Add `--wandb` to the training scripts. Without an account,
`WANDB_MODE=offline` writes the runs to `wandb/`; they can be synced later with `wandb sync`. All
training runs in this repository were logged that way. The local JSON logs in `results/logs/` contain the
same information and are what the tables are built from.

## Reproducing Results

```bash
bash scripts/run_all.sh
```

This runs everything in order. On the RTX 3050 laptop the training runs took about 3.6 hours in
total (logged wall time), plus roughly 10 minutes for retrieval, ranking and the analysis scripts.
`QUICK=1 bash scripts/run_all.sh` runs the same pipeline with 2 epochs per model and one seed into
`results_quick/`. That only checks that everything runs; the numbers are meaningless.

Seeds are fixed: 42, 43 and 44 for the trained models, and 2024 for the validation/test user split.
GPU kernels are not fully deterministic, so re-runs can differ in the third decimal.

## Future Work

- Richer content. Real item text (plot summaries, tags) for the content tower and the hybrid,
  which is where new items and new users could gain most.
- Better inductive cold-start for LightGCN. For example, a learned weight on the
  revealed-rating neighbourhood, or fold-in on top of propagation.
- Ranker training on a recent rolling window. Repeated over several cutoffs, to get variance
  estimates for the strictly temporal setting.
- A larger dataset (MovieLens-25M or an Amazon category) with mini-batch neighbour sampling, to
  see whether learned message passing pays off when the graph is less dense at two hops.
- A retriever that covers more of the long tail, for example popularity-corrected scores or a
  second candidate source, since the ranker cannot recover what retrieval misses.
